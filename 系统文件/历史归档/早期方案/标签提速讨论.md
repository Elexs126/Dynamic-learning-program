是的，这次 50 题 L3 标注的时间和成本都偏高，而且其中相当一部分不是“题目本身难”，而是流程设计和我这次的操作失误造成的。

从文件落盘时间看，大致是：

| 阶段 | 时间 | 说明 |
|---|---:|---|
| 5 个标注 Agent 首轮处理 | 00:39 至 01:10，约 31 分钟 | 5 个 Agent 都对同一份 50 题原始 Markdown 做了完整理解 |
| 合并与恢复 | 01:10 至 01:28，约 18 分钟 | 两组中间结果没有正常落盘，我又写合并脚本、调试编码和 PowerShell |
| 最终 QA | 01:28 至 01:49，约 21 分钟 | QA Agent 重新读取大 JSON 和原题库，期间还被我错误地多次中断 |
| 总墙钟时间 | 约 70 分钟 | 不是纯标注推理时间 |

所以真正花费最大的地方有三个：

1. 5 个 Agent 都重复读取了完整原始文件，包括不需要作为标签输出的参考答案和解析。

2. 方法组、教学诊断组的结果保存失败，导致主 Agent 被迫恢复和重建部分字段。这 18 分钟基本属于流程浪费。

3. QA 阶段处理了约 24 万字节的合并 JSON，而且我错误判断它“卡住”，两次发送中断，进一步拖慢了过程。

金额方面，我这里看不到具体的 API token 用量和账单，所以不能负责任地给出金额数字。但从调用结构看，成本确实不合理：相当于至少进行了“5 次全题语义分析 + 1 次完整 QA”，而且使用了高强度推理。最贵的不是脚本，而是多个 Agent 对同一批题重复理解。

你说的“能不能简单任务拿脚本批量执行”，答案是：完全可以，而且应该这样改。

下一批可以采用：

```text
原始 Markdown
    ↓ 脚本解析、去除答案解析、提取题号/年份/题型/分值/章节
标准化题目 JSON
    ↓
5 个纵向 Agent 只读取精简 JSON 和标签字典
    ↓
脚本自动合并、校验字段、校验分值、校验枚举
    ↓
QA Agent 只处理合并结果和异常项
```

脚本可以直接完成：

- 题号、年份、题型、分值、章节提取；
- 删除参考答案和解题步骤；
- 题目格式清洗；
- 五组 JSON 按 `item_id` 合并；
- 字段缺失、重复题号、分值超限、标签数量超限检查；
- canonical 知识点 ID 规范化；
- 输出最终文件。

真正需要模型判断的，主要是：

- 细粒度知识点；
- 解题方法；
- 题目结构和难度；
- 可能的学生错误；
- 题目之间不容易规则化的语义关系。

而且不必所有任务都使用 `ultra`。常规题可以使用普通或 high 强度模型，只有以下情况再升级：

- 新知识点；
- OCR 严重；
- 图形缺失；
- Agent 之间标签冲突；
- QA 脚本发现异常。

这次做完后，下一批会明显加速，因为已经有了：

- L3 字段结构；
- canonical 知识点 ID；
- 标签枚举；
- 方法和前置条件的写法；
- 题目结构分类；
- QA 检查规则；
- 合并和校验脚本；
- 一批可作为示例的已标注题目。

但加速主要发生在“固定成本”上。相同学科、相同题库格式、相同 L3 schema 的下一批，脚本和标签字典可以直接复用；真正的新题仍然需要语义判断。

工程上，类似 50 题的下一批不应该再以 70 分钟为基准。把输入清洗、合并和 QA 机械检查脚本化后，墙钟时间有机会压到分钟级到十几分钟级，token 成本也会显著下降。此次结果不能作为正常效率基准，因为其中包含了结果落盘失败、脚本调试和错误中断等额外损耗。
